## 3. API route handler conventions

### 3.1 Typical handler shape (observed)

```text
export async function POST(request: NextRequest, { params }: { params: Promise<{…}> })
  1. read servio_session cookie → verifySession(token)          (auth; per-route helper)
  2. role / ownership check                                    (inline or helper)
  3. body = await request.json().catch(() => null)
  4. schema.safeParse(body) (zod)                              (60 safeParse vs 3 parse)
  5. rateLimit(key, limit, windowMs) on sensitive endpoints    (7 routes)
  6. db.* queries; db.$transaction for multi-write ops         (14 files)
  7. conditional updateMany(where: {id, status}) + 409 on race (state transitions)
  8. enqueueBackgroundJob(...) / emitRealtime*(...) after commit
  9. return NextResponse.json(...)
```

Route segment config appears ad hoc: `export const runtime = "nodejs"` (9 files), `dynamic = "force-dynamic"` (2), `revalidate = 0` (1).

## 4. Error handling and logging conventions

| Mechanism | Behaviour | Usage |
|---|---|---|
| `logServerError(event, error, context)` — `src/lib/server-logger.ts` | Writes one-line JSON `{"level":"error","event",…,"message",…context}` to `console.error`; sends exception to Sentry with `event` tag and `servio` context. Designed not to log bodies/secrets. | 13 files |
| Request correlation | `proxy.ts:93-98` sets/propagates `x-request-id`; handlers pass `requestId: request.headers.get("x-request-id")` into `logServerError` context | 6 route files (project requests, project files, verification documents/upload) |

| Swallowed errors | Empty `catch {}` / `.catch(() => undefined \| null \| {})` patterns: ~86 matches. Many are intentional (`request.json().catch(() => null)` → 400), but several `catch {` blocks return generic 500s without logging (e.g. `app/api/auth/[action]/route.ts:714,733`) | grep |

## 7. Rules to follow for new code (derived from the enforced config and the safest existing patterns)

1. Pass `npm run lint` and `npm run typecheck`; format with Prettier settings above (do not run `npm run format` on unrelated files).
2. Import via `@/…`; put server-only modules in `src/lib/` with `import "server-only"`.
3. Before using a Next.js API, check `node_modules/next/dist/docs/` (Next 16: `proxy.ts`, async `params`).
4. In route handlers: authenticate with `verifySession` (prefer the shared `src/lib/auth.ts` helpers over adding another local variant), validate with zod `safeParse`, verify ownership in the DB query `where`, wrap multi-writes in `db.$transaction`, use conditional `updateMany` + 409 for state changes, and trigger emails/realtime only after commit.
5. Log unexpected failures with `logServerError("<domain>.<action>.failed", error, { requestId, userId, … })`; never log secrets, tokens, OTPs or request bodies.
6. Follow the existing error shape of the module you touch (`{ error: string }` is the de facto convention); do not introduce a third envelope.
7. Money: integer amounts only; reuse `calculateMilestoneMoney`/ledger helpers.
8. Schema changes: new forward migration folder, never edit existing migration SQL; run `prisma format/validate/generate`, commit generated client.
