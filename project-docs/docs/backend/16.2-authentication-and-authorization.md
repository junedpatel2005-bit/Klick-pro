# 16.2 Authentication & Authorization

## Purpose

Secure the platform and ensure each user can access only the pages and actions allowed for their role.

## Implemented work

- Email and password registration and login.
- Google OAuth login support where provider credentials are configured.
- Phone verification flow and password-reset flow.
- Signed, HTTP-only session cookies.
- Role-based authorization for Client, Professional, and Admin users.
- Protected API routes that reject unauthenticated users and users with the wrong role.

## How to explain it

Authentication confirms who the user is. Authorization then confirms what that user is allowed to do. For example, a client can post a job, a professional can submit a proposal, and an administrator can manage all marketplace records.

## Detailed security design

The registration process creates an account with a selected marketplace role. Password-based login verifies the submitted password against the stored password hash. OAuth login can be used as an alternative identity provider when Google credentials are configured. The backend creates a signed HTTP-only cookie after successful login; JavaScript in the browser cannot directly read this type of cookie, which reduces exposure to client-side attacks.

On every protected request, the server reads and verifies the session token. It then checks role and ownership. Role checks answer questions such as “is this user an administrator?” Ownership checks answer questions such as “does this client own this job?” Both checks are required: a normal client must not be able to edit another client’s job simply by changing an ID in the URL.

## Authorization examples

| Action                          | Required authorization                                    |
| ------------------------------- | --------------------------------------------------------- |
| Publish or close a job          | Signed-in Client who owns that job                        |
| Submit a proposal               | Signed-in Professional with an active profile             |
| View private project file       | Client or Professional assigned to that project, or Admin |
| Review all verification records | Admin only                                                |
| Manage CMS content              | Admin only                                                |

## Account recovery and verification

The password-reset flow uses a time-limited token delivered by email. The phone-verification flow confirms a phone number through a verification process before marking it as verified. These processes should use production email/SMS provider credentials in a live deployment, and reset or verification tokens must be stored and expired securely.

## Security talking points

- Passwords are never returned from the API or displayed to other users.
- Sensitive routes validate authentication on the server, not only in the UI.
- API input is validated to prevent malformed or unexpected values.
- Administrative features are separated from normal marketplace features by role checks.

## Demonstration

1. Register or sign in as a client and as a professional.
2. Open each role dashboard and show its different functions.
3. Attempt an admin-only route with a non-admin account.
4. Explain that the server validates the session and role before returning protected data.
