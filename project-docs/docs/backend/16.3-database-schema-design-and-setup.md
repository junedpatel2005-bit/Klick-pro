# 16.3 Database Schema Design & Setup

## Purpose

Store marketplace data in a structured, relational, and maintainable database.

## Implemented work

- PostgreSQL database managed through Prisma ORM.
- Data models for users, profiles, jobs, proposals, projects, milestones, files, verification, payments, wallets, CMS content, support, and notifications.
- Relationships between client job posts, professional proposals, accepted projects, milestones, and payments.
- Database migrations and seed-compatible setup.
- Database notification history so users can view older notifications after they sign in.

## How to explain it

Prisma defines the data structure in one schema. PostgreSQL stores the real records. Relationships ensure that a proposal belongs to a job, a job belongs to a client, and a project only starts after a proposal is accepted.

## Detailed data model

The User record is the central identity model. It stores authentication-related information and role, while profile records store client or professional-specific data. A client creates Job records. A professional creates Proposal records linked to a Job. Once the client accepts a proposal, the system creates an active Project and its Milestone records. This gives the platform a traceable path from initial demand to completed work and payment.

Important operational models include verification records, uploaded files, wallet and withdrawal records, disputes/support records, CMS content, and notifications. Keeping these as separate models avoids placing unrelated data into one large table and lets the backend apply more precise permissions.

## Relationship flow

```text
Client User -> Job -> Proposal <- Professional User
                         |
                    accepted proposal
                         |
                         v
                    Project -> Milestones -> Wallet / Payout
```

## Database integrity

The backend uses foreign-key relationships and application-level checks to protect data integrity. A proposal cannot be valid without an associated job and professional. A project should be created only from an accepted proposal. Files are associated with their project or verification context. Notifications point to a recipient and activity source so historical records can be displayed later.

## Migration and environment approach

Prisma schema changes are applied using migrations. This means development, test, staging, and production databases can use the same versioned structure. A new environment needs `DATABASE_URL` and, where required by the hosting provider, `DIRECT_URL`. Seed data can create sample roles and marketplace records for demonstrations without manually inserting records into the database.

## Demonstration

1. Open `prisma/schema.prisma`.
2. Explain the User, Job, Proposal, Project, and Notification relationships.
3. Create a job and proposal, then show the related records in the application.
4. Run migrations or seed data on a fresh development database if needed.
