# 16.7 File Storage (S3 / Cloud) & CDN

## Purpose

Store project attachments safely and allow only authorized users to access them.

## Implemented work

- File type and size validation.
- Private storage keys instead of public, guessable file paths.
- Database records for uploaded project files.
- Authorization checks before downloading protected attachments.
- Local development storage adapter.
- Cloud-storage-ready design for AWS S3 or Cloudflare R2.

## Production requirement

The internal file workflow is implemented. A live deployment still needs an AWS S3 or Cloudflare R2 account, storage credentials, bucket policy, and CDN configuration.

## Detailed storage workflow

The upload flow begins with server-side validation. The backend checks the file’s size and allowed type before assigning a private storage key. It creates a database file record that identifies the uploader, related project or verification record, original file metadata, and storage location. The storage key should be treated as an internal implementation detail rather than a public URL.

When a user requests a download, the backend verifies whether that user owns, participates in, or administers the related record. Only then should it provide access. In cloud storage this normally means creating a time-limited signed URL; it does not mean placing all uploads in a publicly readable bucket.

## Local versus production setup

The current local adapter is useful for development and demonstrating the workflow. Production should replace the adapter configuration with S3 or R2. The application business logic remains the same because the storage adapter isolates provider-specific code.

| Concern          | Development                       | Production                                    |
| ---------------- | --------------------------------- | --------------------------------------------- |
| Storage location | Local/private development storage | S3 or R2 private bucket                       |
| Delivery         | Application-controlled download   | Short-lived signed URL and optional CDN       |
| Secrets          | Local environment                 | Managed environment secrets                   |
| Backup           | Local development copy            | Bucket versioning/lifecycle and backup policy |

## Security talking points

- Validate file type and size before storage.
- Keep project and verification files private by default.
- Verify project membership before download.
- Do not trust the extension alone; production should also inspect content type where appropriate.

## Demonstration

1. Open an active project as an authorized client or professional.
2. Upload an allowed attachment.
3. Show the attachment in the project details.
4. Explain that another unrelated account cannot download the private file.
