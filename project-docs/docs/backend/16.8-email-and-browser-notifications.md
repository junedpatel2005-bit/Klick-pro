# 16.8 Email & Browser Notification Service

## Purpose

Notify the right people about account, job, proposal, and project activity without requiring them to reload the website.

## Implemented work

- SMTP email functions for account verification and password reset.
- Persistent notification records in the database.
- Notification pages and bell indicators for client, professional, and admin experiences.
- Bottom-right toast notifications using Sonner.
- Authenticated Socket.IO server and client connection.
- Live notification rules:
  - New professional registration notifies active clients and admins.
  - New job publication notifies active professionals and admins.
  - New professional proposal notifies the client and admins.
- Admin notification history, including backfilled historical marketplace activity.

## How to explain it

Every important action first creates a database notification record. The server then emits a socket event to the connected recipient. The user gets an instant toast, while the saved record remains visible later in the notification list.

## Detailed event architecture

The notification system has two paths that work together. The persistent path inserts a notification record into PostgreSQL. This path is the source of truth for the bell count and the full notification history. The realtime path emits the same event through Socket.IO to a room associated with the authenticated recipient. This path improves user experience by showing the event immediately.

The browser connects to Socket.IO only after its authentication cookie is available. The server verifies the session before allowing the connection and joins the socket to a user-specific room. This prevents a user from subscribing to another user’s notifications by guessing an identifier.

When an event arrives, the frontend uses the toast component to show a bottom-right message and dispatches a local update so the header bell and notification screen refresh their data. If a user was offline, no message is lost because the notification record remains stored and appears when the user later opens the site.

## Notification responsibility table

| Marketplace event          | Recipients                                                         |
| -------------------------- | ------------------------------------------------------------------ |
| Client registration        | Administrators                                                     |
| Professional registration  | Active clients and administrators                                  |
| Open job published         | Active professionals and administrators                            |
| Professional proposal sent | Job owner and administrators                                       |
| Project/milestone activity | Relevant client, professional, and administrators where configured |

## Email role

Browser notifications are immediate in-app messages. Email is used for account verification, password reset, and can be extended for important activity when a user is offline. SMTP credentials are required for real delivery in production; development can use a test mail service.

## Demonstration

1. Run `npm run dev`.
2. Open two browser sessions with a client and a professional account.
3. Publish a job as the client.
4. Show the professional's bottom-right toast without refreshing the page.
5. Submit a proposal as the professional and show the client and `/admin/notifications` updates.

## Deployment note

Socket.IO requires a persistent Node server. For serverless-only hosting such as standard Vercel functions, use a managed realtime provider instead.
